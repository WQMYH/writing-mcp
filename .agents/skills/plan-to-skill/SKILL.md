description: Transform a plan document set into a runnable execution skill. Input is a plan collection (plan/contract/status/review/test-list docs for one project); output is a SKILL.md with document map, state-resolution protocol, precise routing protocol, fix discipline, and commit rules. The meta-skill first audits the plan structure (single status source, clear file boundaries, split-vs-merge decisions) and refuses to generate from a structurally broken plan. Use when a project has a plan doc set and needs a durable execution skill, or when validating that a plan is skill-ready.

# Plan → Skill 元技能

本 Skill 把"一份计划文档集"转化为"一个可执行执行 Skill"。它不复制计划内容，而是**先审查计划结构、再提取结构化事实、最后生成执行协议**。参考基准：`writing-mcp-plan`（本元技能的第一个验证产物），任何生成的 Skill 应与其结构等价或更优。

## Token 原则（设计之本，一切步骤服从）

- **拆分计划的目的就是省 token**：让每次加载/执行只读需要的文档，不读无关内容。
- 本元技能自身**不得因审查/验证环节增加不必要的 token 消耗**——验证粒度按产出成熟度分级（见步骤 5），能轻则轻，能省则省。
- 生成的 Skill 只含协议不含状态/教训正文，正是为了让它在使用时不携带与当前任务无关的 token。
- 任何"强制复检 / 每次冒烟 / 触发再生成"若比收益消耗更多 token，即舍本逐末，不做。

## 输入约定（plan 文档集）

调用前确认具备以下角色（允许缺失，缺失项在输出中标注"未提供"）：

| 角色 | 典型文件 | 缺失后果 |
|---|---|---|
| 计划/执行顺序 | `*_plan.md`、`*_v2.md` | 无法生成路由，输出降级为"仅状态确定" |
| 契约/协议 | `CONTRACT.md`、schema/ADR 目录 | 无法判定契约影响，路由规则 5 失效 |
| 状态 | `*_STATUS.md`（**必须唯一**） | 违反单一事实源，需先指定 |
| 问题库/审查 | `REVIEW_*.md`、`CONSOLIDATED.md` | 生成规则无输入问题可对照 |
| 测试清单 | `tests/README.md` 或测试目录 | 门禁锚点表无法生成 |

## 处理协议（6 步，顺序执行）

### 步骤 0：计划审查（新增——生成前必须先审查结构）

**目的**：确认计划文档集**是否具备生成执行 skill 的结构前提**；结构缺陷在生成前暴露，而不是生成后靠 skill 的协议硬撑。

**审查项**：
1. **状态文件唯一性**：统计状态角色文档数。>1 → 停止，先裁定唯一状态源（按：代码仓库内 / 随提交维护 / 最贴近代码事实），否则拒绝生成。
2. **文件边界清晰度**：逐文档判断是否混载多种生命周期。典型缺陷：
   - 同一文件同时含"契约/持久决策"与"状态快照"（如计划正文里写测试计数、AUD 关闭表）
   - 同一文件同时含"执行步骤"与"历史审查结论"
   - 状态信息散落 >1 文件（计划/README/状态各写一份）
3. **拆分判定**：若发现文件边界缺陷，输出**拆分建议**（不是直接生成）：
   - 契约/决策 → 独立契约文件（如 `CONTRACT.md`）
   - 状态 → 唯一状态文件（如 `*_STATUS.md`）
   - 执行步骤/门禁 → 计划文件（只引用状态，不复制）
   - 审查/问题库 → 独立审查文件
   - **教训应在计划层已消化**：理想情况下计划文档集本身就按这些边界组织（这正是 writing-mcp 的现状）；步骤 0 只是确认而非补丁。若结构确需拆分，**输出建议后由调用方（人/上级流程）决定是否现在拆分**——不强制本元技能现场复检（那会额外消耗 token 且越界）；调用方拆分完成后重新调用本元技能即可。

**输出**：`{ 结构判定: 合格|需拆分, 拆分建议[], 唯一状态文件: <path> }`。仅"合格"进入步骤 1；"需拆分"则输出建议并停下，由调用方决定是否拆分后重来。

### 步骤 1：探测门禁命令（读 package.json，不得伪造）

- 读目标仓库 `package.json` 的 `scripts`，记录 `check`/`test`/`benchmark`/`build` 的真实命令。
- 若脚本名与计划文档写的不一致，**以 package.json 为准**并在输出中标注偏差。
- 记录运行环境事实（Node 版本、沙箱限制如 vitest spawn EPERM），写入"已知边界"。

### 步骤 2：识别文档地图

- 从计划文档中提取它**引用了哪些文档**（相对路径/链接），每个文档的角色（契约/状态/审查/测试/IDEAS）。
- 每个文档标注"何时必须读"（动手前/改接口前/恢复核对/新增测试时）。
- 产出：文档地图表（主题 | 文档路径 | 何时必读）。

### 步骤 3：提取里程碑与门禁

- 从计划中提取每个 Step/Milestone：编号、AUD 或任务清单、**完成门禁**（验收条件）、**预期状态**（未开发/进行中/已完成——从计划自身声明判断，不是代码）。
- 产出：AUD/任务锚点表（Step | 任务 | 代码锚点占位 | 回归测试占位）。
- **代码锚点与测试文件名留占位**，由生成的 Skill 在使用时通过状态确定协议现场核对——锚点表不是状态，是定位线索。

### 步骤 4：生成 SKILL.md（按下方模板）

- 用模板生成，**铁律：生成的 Skill 不得包含具体状态**（测试计数、AUD 关闭表、已完成/未完成清单），**也不得包含历史教训正文**（教训已固化在元技能的生成规则，产物只承载由教训推导出的协议——教训若进产物，未来更新教训会导致每个已生成 skill 过期）。
- 产物结构：文档地图 / 恢复协议 / 状态确定 / 精准路由 / 任务代码锚点 / 修复纪律 / 提交规范 / 已知边界。**无"历史教训"章节**。

### 步骤 5：验证（分级，按 Token 原则）

**轻量必查（每次生成后，低成本，不得省）**——纯结构核对，不运行产物：
- 对同一输入，生成的 Skill 与 `writing-mcp-plan` 相比应满足：① 有状态确定协议；② 有精准路由协议；③ 文档地图完整；④ 无状态快照；⑤ 无历史教训正文（教训只存在于元技能规则）；⑥ 有门禁命令且来自 package.json。
- 不满足任一 → 修订生成结果，不交付。

**冒烟验证（由智能体自行判断是否进行，非必做）**：
- **仅在产出成熟、接近交付时**（如首次生成、结构大改后）才执行；日常小改、结构核对已够时**不做**（省 token）。
- 若做：用产物跑一次最小恢复协议（读文档地图 → 跑门禁命令中成本最低的一个 → 确认不报错），不跑全量。
- 判定权在智能体：功能齐全程度、变更幅度、成本权衡由当前上下文判断，**不设硬性阈值**。

## 生成规则（教训固化，每条对应一次真实事故——只存在于元技能，不进产物）

1. **状态单一事实源**（事故：测试计数 13/14/15/12 四文件漂移）
   → 步骤 0 审查唯一性 + 生成的 Skill 声明唯一状态文件。
2. **完成判定绑定机器门禁**（事故：AUD-021 声称完成但测试失败）
   → 生成的 Skill 必须含状态确定协议：读声称 → 跑门禁 → 核对代码锚点+测试 → 分类。门禁全绿+回归测试存在才算完成。
3. **代码超前于计划要自动可见**（事故：AUD-005/015/020/022 已实现但文档未记）
   → 状态确定协议第 4 步捕获"超前完成"并路由先回写状态。
4. **未开发里程碑的门禁不是缺陷**（事故：把 M4/M5 未关闭当回归审阅）
   → 精准路由把"预期未开发"里程碑的 AUD 排除出候选，除非前置 Step 门禁全关。
5. **开发中 vs 已发布**（事故：AUD-025 方案先按已发布约束设计）
   → 路由规则含"每次修复前判定开发中/已发布"：决定能否改契约、能否依赖 SDK 行为、失败形态是否保守。
6. **测试先行 + 契约纪律**（计划 §13.2）
   → 修复纪律固化：先写失败测试 → 实现 → 门禁 → 契约 amendment/ADR → 提交。
7. **计划结构缺陷要先拆分**（事故：单一计划文档承载契约+状态+执行四层生命周期，导致状态漂移）
   → **教训应在计划层已消化**：计划文档集本身应按健康边界组织；步骤 0 是确认而非补丁。确需拆分时输出建议、由调用方执行，不强制现场复检。

## 输出模板（生成的 SKILL.md 骨架）

```markdown
---
name: <project>-plan
description: <一句话：执行 <计划名>：恢复、门禁、任务路由、文档导航、提交规则>
version: 0.1.0
---

# <Project> 计划执行 Skill

本 Skill 由 `plan-to-skill` 元技能生成（步骤 0 计划审查 + 生成规则）。是 <计划名> 的**操作手册**：在哪读什么、恢复时做什么、按什么顺序修、何时提交。不是契约本身。

## 文档地图（先读这个，不清晰就点开原文）
| 主题 | 文档 | 何时必须读 |
|---|---|---|
| 执行计划 | <path> | 每次动手前 |
| 契约 | <path> | 改接口/schema/验收前 |
| **状态（唯一事实源）** | <path> | 每次恢复核对 |
| 问题库/审查 | <path> | 决定修哪个任务时 |
| 测试清单 | <path> | 新增/删除测试时 |
（其他按输入补）

**状态单一事实源纪律**：<状态文件> 是唯一状态文件；其他文档只引用不复制；发现别处记载状态以它为准并修正。

## 恢复协议（每次继续先做）
<步骤 1 探测到的门禁命令，来自 package.json>
核对：当前里程碑、最近门禁、未提交改动、fixture/语料是否仍在。

## 状态确定协议（替代一切静态进度快照）
<步骤：读声称 → 跑门禁 → 核对锚点+测试 → 分类（确认/虚报/超前/预期未完成）→ 输出可信状态；不落盘，不污染唯一状态源>

## 精准路由协议（状态确定后，输出下一步）
<规则：顺序推进不跳步 / 超前项先回写 / 未开发里程碑排除 / 契约影响判定 / 开发中判定>

## 任务代码锚点（路由判定用，非状态）
| Step | 任务 | 代码锚点 | 回归测试 |
（占位，使用中现场核对）

## 修复纪律
1. 先写失败回归测试，再实现。
2. 每完成一个任务：跑全部门禁，全绿才继续。
3. 公共输出/schema/错误码变化 → amendment 或 ADR；索引 schema → 重建不迁移。
4. 完成判定绑定机器门禁；不得凭文档自述。
5. 闭环：完成 → 更新唯一状态文件 → 重新状态确定 → 路由下一目标。

## 提交规范
- 提交点：可独立回滚修复 / 子门禁完成 / 计划调整 / 稳定阶段成果。
- 提交信息：标题 + 正文（动机/改动/验证）。
- 不提交：书稿/私有数据/生成产物/未授权审查文件。

## 已知边界
<步骤 1 探测到的环境限制 + 输入未提供的角色>
```

## 使用示例（对照基准）

输入：`Writing_MCP_Server_v2.md` + `M0_CONTRACT.md` + `IMPLEMENTATION_STATUS.md` + `REVIEW_2026-08-15_CONSOLIDATED.md` + `tests/README.md` + 仓库 `writing-mcp/`。
流程：步骤 0 审查（状态唯一=IMPLEMENTATION_STATUS ✅、文件边界✅ 因已在计划层消化并拆分）→ 步骤 1 门禁 → 步骤 2 文档地图 → 步骤 3 里程碑 → 步骤 4 生成 → 步骤 5 轻量验证（产出成熟时再按需冒烟）。
预期输出：与 `writing-mcp-plan`（v0.7.0 起）结构等价，且**无历史教训章节**。
验证：按步骤 5 轻量六项标准比对；冒烟由智能体判断。

## 铁律（违反即重做）

- 生成的 Skill **不得包含具体状态**（计数、关闭表、进度）；状态由协议现场确定。
- 生成的 Skill **不得包含历史教训正文**——教训只存在于元技能生成规则，产物只承载协议。
- 门禁命令必须来自 `package.json`，不得照抄计划文档。
- 唯一状态文件不明确 → 拒绝生成，先裁定。
- **计划结构缺陷（文件边界不清/状态多源）→ 输出拆分建议并停下，由调用方决定是否拆分后重来；不得带着病态结构硬生成。**
- **Token 优先**：任何验证/复检/冒烟以最小消耗为原则；能轻则轻，能省则省，不做舍本逐末的强制环节。
