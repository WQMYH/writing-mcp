# Plan → Skill 元技能

本 Skill 把"一份计划文档集"转化为"一个可执行执行 Skill"。它不复制计划内容，而是**提取计划的结构化事实**并**生成执行协议**。参考基准：`writing-mcp-plan`（由本元技能的方法手工形成的第一个样例，v0.5.0），任何生成的 Skill 应与其结构等价或更优。

## 输入约定（plan 文档集）

调用前确认具备以下角色（允许缺失，缺失项在输出中标注"未提供"）：

| 角色 | 典型文件 | 缺失后果 |
|---|---|---|
| 计划/执行顺序 | `*_plan.md`、`*_v2.md` | 无法生成路由，输出降级为"仅状态确定" |
| 契约/协议 | `CONTRACT.md`、schema/ADR 目录 | 无法判定契约影响，路由规则 5 失效 |
| 状态 | `*_STATUS.md`（**必须唯一**） | 违反单一事实源，需先指定 |
| 问题库/审查 | `REVIEW_*.md`、`CONSOLIDATED.md` | 历史教训占位留空 |
| 测试清单 | `tests/README.md` 或测试目录 | 门禁锚点表无法生成 |

**发现多个状态文件时必须先裁定唯一状态源**（按：代码仓库内 / 随提交维护 / 最贴近代码事实），否则拒绝生成。

## 处理协议（5 步，顺序执行）

### 步骤 1：探测门禁命令（读 package.json，不得伪造）

- 读目标仓库 `package.json` 的 `scripts`，记录 `check`/`test`/`benchmark`/`build` 的真实命令。
- 若脚本名与计划文档写的不一致，**以 package.json 为准**并在输出中标注偏差。
- 记录运行环境事实（Node 版本、沙箱限制如 vitest spawn EPERM），写入"已知边界"。

### 步骤 2：识别文档地图

- 从计划文档中提取它**引用了哪些文档**（相对路径/链接），每个文档的角色（契约/状态/审查/测试/IDEAS）。
- 每个文档标注"何时必须读"（动手前/改接口前/恢复核对/新增测试时）。
- 产出：文档地图表（主题 | 文档路径 | 何时必读）。

### 步骤 3：提取里程碑与门禁

- 从计划中提取每个 Step/Milestone：编号、AUD 或任务清单、**完成门禁**（验收条件）、**预期状态**（未开发/进行中/已完成——从计划自身声明判断，不是代码）。
- 产出：AUD/任务锚点表（Step | 任务 | 代码锚点占位 | 回归测试占位）。
- **代码锚点与测试文件名留占位**，由生成的 Skill 在使用时通过状态确定协议现场核对——锚点表不是状态，是定位线索。

### 步骤 4：生成 SKILL.md（按下方模板）

- 用模板生成，**铁律：生成的 Skill 不得包含具体状态**（测试计数、AUD 关闭表、已完成/未完成清单）。只含"如何确定状态"的协议。
- 模板中的「历史教训」段落按输入项目的情况填充；无输入时留空占位并注明"运行后补充"。

### 步骤 5：验证（对照基准）

- 对同一输入，生成的 Skill 与 `writing-mcp-plan` 相比应满足：① 有状态确定协议；② 有精准路由协议；③ 文档地图完整；④ 无状态快照；⑤ 有门禁命令且来自 package.json。
- 不满足任一 → 修订生成结果，不交付。

## 生成规则（教训固化，每条对应一次真实事故）

1. **状态单一事实源**（事故：测试计数 13/14/15/12 四文件漂移）
   → 生成的 Skill 必须声明唯一状态文件，文档地图将其标为"**唯一事实源**"，且任何"当前状态"判断以此为准。
2. **完成判定绑定机器门禁**（事故：AUD-021 声称完成但测试失败）
   → 生成的 Skill 必须含状态确定协议：读声称 → 跑门禁 → 核对代码锚点+测试 → 分类（确认/虚报/超前/预期未完成）。"完成"只有门禁全绿+回归测试存在才算。
3. **代码超前于计划要自动可见**（事故：AUD-005/015/020/022 已实现但文档未记）
   → 状态确定协议第 4 步必须捕获"超前完成"并路由先回写状态，避免重复劳动。
4. **未开发里程碑的门禁不是缺陷**（事故：把 M4/M5 未关闭当回归审阅）
   → 精准路由必须把"预期未开发"里程碑的 AUD 排除出候选，除非前置 Step 门禁全关。
5. **开发中 vs 已发布**（事故：AUD-025 方案先按已发布约束设计）
   → 路由规则必须包含"每次修复前先判定开发中/已发布"：决定能否改契约、能否依赖 SDK 行为、失败形态是否保守。
6. **测试先行 + 契约纪律**（计划 §13.2）
   → 生成的 Skill 的修复纪律必须固化：先写失败测试 → 实现 → 门禁 → 契约 amendment/ADR → 提交。公共输出/schema/错误码变化必须带 amendment。

## 输出模板（生成的 SKILL.md 骨架）

```markdown
---
name: <project>-plan
description: <一句话：执行 <计划名>：恢复、门禁、任务路由、文档导航、提交规则>
version: 0.1.0
---

# <Project> 计划执行 Skill

## 文档地图（先读这个，不清晰就点开原文）
| 主题 | 文档 | 何时必须读 |
|---|---|---|
| 执行计划 | <path> | 每次动手前 |
| 契约 | <path> | 改接口/schema/验收前 |
| **状态（唯一事实源）** | <path> | 每次恢复核对 |
| 问题库/审查 | <path> | 决定修哪个任务时 |
| 测试清单 | <path> | 新增/删除测试时 |
（其他按输入补）

**状态单一事实源纪律**：<状态文件> 是唯一状态文件；其他文档只引用不复制；发现别处记载状态以它为准并修正。

## 恢复协议（每次继续先做）
<步骤 1 探测到的门禁命令，来自 package.json>
核对：当前里程碑、最近门禁、未提交改动、fixture/语料是否仍在。

## 状态确定协议（替代一切静态进度快照）
<步骤：读声称 → 跑门禁 → 核对锚点+测试 → 分类 → 输出可信状态>

## 精准路由协议（状态确定后，输出下一步）
<规则：顺序推进不跳步 / 超前项先回写 / 未开发里程碑排除 / 契约影响判定 / 开发中判定>

## 任务代码锚点（路由判定用，非状态）
| Step | 任务 | 代码锚点 | 回归测试 |
（占位，使用中现场核对）

## 修复纪律
1. 先写失败回归测试，再实现。
2. 每完成一个任务：跑全部门禁，全绿才继续。
3. 公共输出/schema/错误码变化 → amendment 或 ADR；索引 schema → 重建不迁移。
4. 完成判定绑定机器门禁；不得凭文档自述。
5. 闭环：完成 → 更新唯一状态文件 → 重新状态确定 → 路由下一目标。

## 提交规范
- 提交点：可独立回滚修复 / 子门禁完成 / 计划调整 / 稳定阶段成果。
- 提交信息：标题 + 正文（动机/改动/验证）。
- 不提交：书稿/私有数据/生成产物/未授权审查文件。

## 已知边界
<步骤 1 探测到的环境限制 + 输入未提供的角色>

## 历史教训（本项目的）
<输入项目的问题库提炼；无则留占位>
```

## 使用示例（对照基准）

输入：`Writing_MCP_Server_v2.md` + `M0_CONTRACT.md` + `IMPLEMENTATION_STATUS.md` + `REVIEW_2026-08-15_CONSOLIDATED.md` + `tests/README.md` + 仓库 `writing-mcp/`。
预期输出：与 `writing-mcp-plan`（v0.5.0）结构等价——文档地图 / 恢复协议 / 状态确定 / 精准路由 / 代码锚点 / 修复纪律 / 提交规范 / 已知边界 / 历史教训。
验证：按步骤 5 五项标准逐条比对。

## 铁律（违反即重做）

- 生成的 Skill **不得包含具体状态**（计数、关闭表、进度）；状态由协议现场确定。
- 门禁命令必须来自 `package.json`，不得照抄计划文档。
- 唯一状态文件不明确 → 拒绝生成，先裁定。
